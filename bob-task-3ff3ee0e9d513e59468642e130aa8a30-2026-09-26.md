### Gaps Requiring Remediation

Two **minor partial-falsifiability** defects were found. The tests exist and are doc-derived, but each has an assertion loophole that lets a specific bug through undetected.

**Gap 1 — W4.2 hold-leaks-into-available**
In [`tests/clause-W4.test.ts:39`](tests/clause-W4.test.ts:39), the it-block only asserts `pending ≥ 0` and `available ≥ 0`. A defect where adding an auth-hold wrongly increments `available` would not be caught. The spec says hold funds **MUST NOT** be included in `available`. The fix is to assert `available` does **not increase** after a hold is placed.

**Gap 2 — W6.3 half-open timing disjunction**
In [`tests/clause-W6.test.ts:79`](tests/clause-W6.test.ts:79), the assertion is `expect(open === 'open' || open === 'half-open').toBe(true)`. This accepts `half-open` while failures are still accumulating, which is exactly the behaviour the spec forbids. The fix is to tighten line 79 to `expect(open).toBe('open')` and add a separate test for the half-open-after-settle-window transition.

### Gap 1 — W4.2 [`tests/clause-W4.test.ts:39-53`](tests/clause-W4.test.ts:39)

**Before:** Two calls to `getBalances` with only `≥ 0` guards. No assertion prevented hold funds from appearing in `available`.

**After — three assertions, all derived from the spec:**
```
expect(b.pending).toBe(500)             // hold lands in pending
expect(b.available).not.toBe(8000)      // MUST NOT include the hold  ← new bite
expect(b.available).toBe(7500)          // hold excluded from available
```
The middle assertion is the falsifiability trigger: if any implementation adds the 500-cent hold to `available` instead of `pending`, `available` returns 8000 and `not.toBe(8000)` fails immediately.
