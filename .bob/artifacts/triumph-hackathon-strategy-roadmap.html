TRIUMPH — 3-Court Dev Tool

Hackathon Strategy Roadmap · YC Product Partner Analysis

Phase 1 · Core Loop Analysis

TRIUMPH is a model-agnostic VS Code extension that transforms any AI coding agent into a disciplined, spec-grounded quality auditor — running three deterministic courts (spec-witness, coverage-honesty audit, and incident forensics) over any repo, using the user's own model, with zero API keys and zero hallucination surface in the engine.

Primary pain point: AI-generated code passes coverage gates and silences CI while silently violating the written spec and being covered by tautological tests that can't catch real mutations — coverage is lying, and no one tool catches all three failure modes at once.

Core loop verdict: STRONG. The three-court method is genuinely differentiated — REDLINE's implementation wall is a real engineering constraint, SPLITBRAIN's falsifiable trust-gap math is not a wrapper, and WARPATH's fixture-grounded postmortem is novel. The multi-host model (Claude/Bob/Codex/GPT all plugging into the same engine without any code change) is a force multiplier for demo coverage. The core loop is not weak; the risk is that it requires 90 seconds of explanation before judges get it.

REDLINE Red-Gutter Inlay Decorations
When REDLINE returns a red clause, the extension injects VS Code editor decorations (gutter icons + inline ghost text) on the exact source lines whose spec anchor maps to a failing clause — a red stop sign in the gutter next to src/payment.ts:42 with ⚠ W07 failing inline. Not a report panel — the editor itself turns red.
Judges watching a live demo have never seen a spec-clause failure rendered as a first-class editor decoration. It makes the abstract "spec divergence" problem viscerally visible on real code.

The Implementation Wall as a Formal Provable Property
Extend assertNotWalled() in the MCP engine to emit a machine-readable wall_audit record in every REDLINE result: the exact set of filesystem paths requested during the run, with a boolean wall_respected: true/false and a cryptographic hash of the test directory at time-of-run. The HTML report renders a "Wall Certificate" section. The claim "this verdict was reached without seeing the implementation" becomes a verifiable, inspectable artifact — not a promise.
This is the kind of formal correctness argument that PhD judges and senior engineers immediately recognize as real engineering. It turns a design principle into a tamper-evident proof.
SPLITBRAIN Async Streaming via Server-Sent Events Build Now
Mutation runs take minutes. Instead of polling splitbrain_status on an interval, expose a /api/jobs/:jobId/stream SSE endpoint from the dashboard server that streams data: {elapsed, killed, survived, remaining} as Stryker emits per-mutant results. The dashboard and the VS Code panel progress log both consume the same stream. The judge sees a live kill-rate climbing in real time like a stock ticker.
SSE over stdio MCP with a fan-out to both a browser dashboard and a VS Code webview, all sourced from live Stryker stdout parsing, is a legitimately hard multi-surface streaming architecture. It demos spectacularly — numbers moving is always compelling.

One-Command CI Badge Export (triumph-report --ci)
Add a --ci flag to triumph-report.js that writes a GitHub Actions-compatible ::set-output block and a triumph-badge.json (shields.io endpoint format) containing REDLINE clause counts, SPLITBRAIN trust gap, and WARPATH status. A GitHub Actions workflow file is materialized by triumph-setup --host github-actions. The repo's README can now display a live TRIUMPH health badge. Judges can see it on the northstar repo right now.
Every serious open-source project has CI badges. A project that installs its own badge endpoint is signaling it is infrastructure, not a demo. This requires ~2 hours and is permanently visible on the repo during the hackathon presentation.
Triumph Report as a Portable Signed Snapshot (POST /api/import already exists)
The /api/import endpoint exists but is undiscoverable. Build a one-click "Share report" button in the dashboard that serializes the current run as a self-contained signed JSON bundle and copies a triumph://import?data=... deep-link to the clipboard. Anyone with the extension installed can paste the link to import and inspect the exact run — clause verdicts, trust gap, postmortem — with no server, no account, no shared filesystem.
This is the "it works offline and across machines" demo moment that proves the architecture is sound. It also demonstrates that the engine output is genuinely portable and model-free — the same JSON works everywhere because there is no model in the data path.
Phase 3 · ROI Triage

Impact vs. Implementation Time Matrix

The Two Features to Build Right Now

① Live Trust-Gap Status Bar Ticker

Priority 1
Why: The single biggest weakness of TRIUMPH in a demo context is that judges need 90 seconds to understand what they're looking at. A status bar item that reads TRIUMPH ▸ 🟢11 🔴2 | gap 34% | WARPATH clear eliminates that problem entirely. The product explains itself the moment VS Code opens. It also turns every subsequent demo action — running a court, watching numbers change — into a visible, trackable feedback loop. This is your opening slide, your product screenshot, and your live demo all in one.
Effort: 2–3 hours. The data is already flowing through the extension panel (src/panel.js → src/actions.js). Hook into the same result callbacks and write to a vscode.StatusBarItem. No new data pipeline, no new API surface.

② SPLITBRAIN Live SSE Streaming

Priority 2
Why: The current async poll model (splitbrain_mutate → splitbrain_status) is technically correct but visually dead. Mutation tests are the hardest part of the demo to sell because judges watch a spinner for 2 minutes and disengage. Replacing that with a live "kill-rate climbing" counter — streaming parsed Stryker stdout into the dashboard via SSE — transforms the wait from a liability into your best demo moment. A live ticker of "Killed: 47/120 mutants, 3 tautologies caught so far" is more compelling than any static report.
Effort: 3–4 hours. The dashboard server (dashboard/server/app.js) already speaks HTTP. Add one SSE endpoint that consumes the Stryker child process stdout line-by-line (the process is already spawned in lib/runners.js via spawnCollect), parse the Stryker progress output, and fan it out to any connected SSE clients. The VS Code panel's log already renders streaming lines. The bridge architecture is already there.
